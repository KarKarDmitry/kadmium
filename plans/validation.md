# Слой валидации — `validationDSL → validationIR → adapter`

**Статус:** 💤 Не начат. Ничего не реализовано. Ниже — результат обсуждения
2026-10-02, фасады и найденные в коде препятствия.

**Важность:** 🟡 Medium

**Направление:** по образу `sql-pg` — контракт-пакет + адаптер + подключение в
конфиг. Отдельные пакеты при этом, скорее всего, не нужны (см. «Пакеты»).

---

## Исходная постановка

Валидация в целом должна выглядеть как работа с `sql-pg`. Не хочется смешивать
model DSL с DSL валидации: `f.string` — это схема, правило «email похож на
email» — это другое. Слой ожидается заметно проще ORM-слоя, поэтому
итеративность не предполагается.

Найденные в коде препятствия, которые влияют на дизайн:

- **`spec.min`/`spec.max` уже объявлены в DSL и мертвы.** `f.string.min(18)`,
  `f.number.min(0)`, `f.datetime.min(...)` кладут значения в `spec` и выживают в
  `FieldIR.spec`, но их не читает никто: в `sql-pg/src/diff/types.ts` из `spec`
  берутся только `db_type` (`:160`) и `default` (`:214`). DML их тоже не
  использует. Значит фундамент есть, но лежит в схемном мешке `spec`, который
  предназначен не для этого.
- **`ModelIR` уже упоминает Validation как потребителя.** `ir/index.ts:5-7`:
  «ORM, Validation, Forms, Codegen читают только IR». Т.е. направление
  заложено, но контракта нет.
- **C10 из `plans/project-review.md` ждёт этот слой.** `create({})` с неизвестными
  ключами молча проходит через `mapDmlData` (`orm/builders/upsert-helpers.ts:141`,
  `mapped[ir.fields[k]?.alias ?? k] = …` — неизвестный ключ падает в себя же).
  Там же записано, что это «отдельный модуль валидации данных на уровне адаптера».
- **`checkHealth` — готовый прецедент для data-уровня.** Схемная проверка уже
  сделана по форме `IR → адаптер → issues`. Валидация была бы её близнецом по
  данным.

## Фасад записи

Три варианта места объявления правил рассматривались.

| Вариант | Инфраструктура | Вердикт |
|---------|----------------|---------|
| 1. `$validation(): { field: rule[] }` — plain-объект | ~0 | ❌ безымянные строковые ключи: опечатка молчит, компилятором не проверяется |
| 2. `$validation()` + билдер правил | ~0 | ✅ выбран |
| 3. отдельные файлы + `validationSources` в конфиге | много | ❌ второй глоб + второй импортёр + свой маркер + свой реестр |

**Причина, по которой вариант 3 отпадает именно на фоне этой кодовой базы:**
`ModelImporter` (`core/model-importer.ts`) обходит экспорты файлов и берёт всё,
что помечено `MODEL_MARKER`. Метод на классе находится сам — ни glob, ни конфиг,
ни второй реестр не нужны. `ModelRegistry.register()` уже делает
`new ModelClass()` и зовёт `compileModel(instance)`
(`core/model-registry.ts:22-24`), рядом кладётся вызов `$validation()`.

**Форма (вариант 2):**

```ts
// src/models/user.ts
import { Model, f } from '@karkardmitry/kadmium-core';

export class User extends Model {
  email = f.string;
  age = f.number;
  amount = f.number.decimal;
  fee = f.number.decimal;
  active = f.bool;

  static $validation() {
    return rules((r, fields) => [
      r.email.format('email').max(255),
      r.age.range(18, 120),

      // метка не обязана быть именем поля — тип живёт в операндах
      total: [r.lte(r.add(fields.amount, fields.fee), 1000)],
    ]);
  }
}
```

Два разных объекта, и путать их нельзя:

- `fields` — **минимальные типы**: `email → string`, `age → number`. Ровно та
  «минимальная проверка, что строка это строка, а число это число». Тип живёт в
  операнде, поэтому `r.add(fields.email, fields.fee)` не компилируется, а метка
  `total` не обязана быть полем.
- `r` — **билдер правил**, адресует поля и строит цепочки.

Ключ объекта — метка для отчёта, не поле. Это то, что делает кросс-полевые
правила возможными без второго синтаксиса.

### Короткаты из `f.*`

`f.string.min(18)` / `.max()` / `f.datetime.min(...)` не убираются, а становятся
шорткатами: билдер поля копит правила прямо в `spec`, `compileModel` переносит их
в validation-IR той же модели. Один источник истины, ломающего изменения нет,
уже написанное у пользователей намерение начинает работать.

### Кросс-полевые выражения — двурежимный IR

Ключевое требование: у правила **две проекции** — SQL для аудита по данным и JS
для проверки конкретной записи. Произвольное JS-замыкание даёт только одну.

Рассматривались два пути:

- **Два вида правил, у каждого свой режим.** Кросс-поле через JS-предикат
  работает в `.validate()`, но не аудируется — и аудит обязан сказать «правило
  непроверяемо», а не молча пропустить. Дёшево сегодня, но полнота аудита ломается.
- **Крошечный двурежимный IR выражений** — выбран. Узлы умеют и `toSql()`, и
  `eval(row)`, поэтому любое правило работает в обоих режимах.

```ts
r.lte(r.add(fields.amount, fields.fee), 1000)
r.check('active_needs_email', ['active', 'email'], r => !r.active || r.email !== '')
```

Потолок задаётся жёстко: арифметика, сравнения, литералы, фиксированный белый
список функций (`length`, `lower`, `abs`). Без произвольных вызовов — иначе это
расползётся в язык запросов.

Кросс-модельные правила переиспользуют уже существующий `FilterProxy` с `.eq()`
(его же берёт `upsert-helpers.ts:129`) — новой машинерии для них не нужно.

## `injectWhere` — это фильтр записи, не валидация

```ts
r.injectWhere('filter: no age', (u) => sql`${u.age} is not null and ${u.age} != 0`)
r.injectWhere('filter: no age', (u) => and(u.age.notNull, u.age.neq(0)))
```

Предикат кладётся в WHERE запроса записи, поэтому строка, не прошедшая правило,
**просто не пишется**. Такое правило никогда не может бросить ошибку — в этом
весь смысл инъекции.

Отсюда два следствия:

- **Маркер `skip` на методе избыточен**: политика уже закодирована в механизме.
  Вместо булева флага — разные типы правил, потому что у них разные права:
  `r.check(...)` может бросить и пропустить, `r.injectWhere(...)` только
  фильтрует и в `throw` не участвует.
- **В отчёте аудита это видно явно**: «правило `no age` — фильтр, 12 строк
  отсечено», а не «12 нарушений». Иначе `kadmium validate` врёт: он находит
  строки, которые при записи просто не попали бы.

Отфильтрованные строки не видны вызывающему: `insertMany` из 100 вернёт 97.
Отлаживается это через `.sql()` — совпадает с философией репозитория, где
`.sql()` единственный способ увидеть, что реально уедет в базу.

## Фасад использования

```ts
const res = await app.validate.run();                        // весь набор
const res = await app.validate.run({ model: User });         // одна модель
const res = await app.validate.run({ collection: 'user', limit: 100 });
```

`ValidationResult` — плоский, как `HealthCheckResult`. Нарушение обязано нести
адрес строки, иначе на реальных данных оно бесполезно:

```ts
interface Violation {
  rule: string;        // 'email_format'
  kind: 'rule' | 'filter';
  collection: string;  // 'user'
  pk: Record<string, unknown> | null;
  message: string;
  sql: string;         // почему — отладка, как db:sql для схемы
}
```

CLI — тонкая обёртка над тем же кодом, ровно как `dbCheck` оборачивает
`checkHealth` (`cli/db.ts:50`). Один и тот же путь: правила компилируются в SQL
«найди строки, где нарушено правило», адаптер исполняет, ядро отдаёт результат,
CLI добавляет форматирование и код выхода. Одна операция на все правила через
`UNION ALL`, не N запросов.

```
kadmium validate                 # весь набор, exit 1 при нарушениях
kadmium validate User            # одна модель
kadmium validate --limit 50      # не жрать память на большой таблице
```

Отдельный глагол, не `db:*`: `db:*` про схему, это про данные. И не часть
`db:push` — валидация про данные, push про DDL, смешивать нельзя.

## Фасад в ORM: `.validate()` терминалом

```ts
await orm.insert(User).values(d).validate().go();
await orm.insertMany(User).values(rows).validate('skip').go();
```

Терминал, а не неявный хук в `go()`: иначе `go()` становится скрытым сетевым
вызовом, которого нет в коде. Место уже есть — `InsertBuilder` держит
`_requireValues()` и отдаёт терминалы из `_finalizer()`
(`orm/builders/insert.ts:137-181`), `.validate()` встаёт рядом с `returning()`.

**Асимметрия по типам, а не проверка в рантайме.** Для одиночного `insert`
`'skip'` бессмыслен — пропустить одну строку из одной нельзя. Репозиторий к
этому строг («отсутствие методов на типе — основной защитник», `insert.ts:42`),
поэтому разводим на уровне типов:

```ts
insert(User).values(d).validate()                        // бросит, выбора нет
insertMany(User).values(rows).validate('throw')
insertMany(User).values(rows).validate('skip')
```

При `'skip'` `insertMany` возвращает меньше строк, чем подано. Список
пропущенных должен быть доступен — иначе тихая потеря данных.

## Пакеты

`SqlAdapter` уже умеет `toSql` (чистый рендер), `execute` и `raw`. Если правила
компилируются в SQL, рендерщик живёт рядом с `sql-generator.ts`/`ddl-sql.ts` в
`sql-pg`, конфиг не меняется вообще, и бесплатно достаются `-> sql()`,
параметризация и PG.

**Отдельный контракт `ValidationAdapter` + новый пакет оправдан только если
валидация должна меняться независимо от SQL** — in-memory, мост к zod,
не-PG цель. Иначе: `ValidationIR` и DSL в `core`, рендер правил в `sql-pg`,
ноль новых пакетов. Подключение в конфиг, если понадобится, механическое:
`modules.validation` рядом с `modules.sql` и ещё один `ModuleSlot`
(`core/kadmium-app.ts:17-29`).

## Правила в базе — второй этап, единственная настоящая гарантия

`CHECK`-констрейнт добавляется тем же способом, что и уникальный индекс из
`a962069`: `DbCheck` + интроспекция каталога + `add-check`/`drop-check` + рендер
через `computeDiff`/`applyDiff`. «Остальные БД под вопросом» — это ровно тот
же аргумент, по которому уже приняты FK и индексы: `DbDdlAdapter` per-adapter.

Причина, по которой это не альтернатива, а дополнение: **превентивная проверка
перед записью — TOCTOU**. Между проверкой и `INSERT` другая транзакция успевает
вставить дубль. Она даёт ощущение гарантии, которой нет. Поэтому pre-flight
либо не делаем вовсе, либо честно называем best-effort под формы, а инвариант
обеспечиваем констрейнтом.

## Блокирующая находка: нечем объявить поле

Правило нельзя написать для поля, которое нечем объявить. Проверено:

- `FieldType` и `pgType` уже знают `bigint`, `float`, `numeric`, `uuid`, а для
  неизвестного типа `pgType` падает в `text` (`sql-pg/src/diff/types.ts:155-192`).
- DSL при этом даёт только `f.string`, `f.bool`, `f.number` (+`.decimal`),
  `f.datetime` (+`.date`, `.time`), `f.pk` (+`.bigint`, `.uuid`), `f.ref`.
- **Нет** `f.text`, `f.json`, `f.array`, нет не-PK `f.bigint`/`f.uuid`.

Порядок, который из этого следует:

- `f.text`, `f.uuid`, `f.bigint` — отдельным маленьким PR. `codegen` generic по
  `tsType` (`codegen/generate-model.ts:85`), не хватает в основном билдера.
- `json`/массивы — **отдельным решением позже**. У `json` принципиально другое
  семейство правил (валидация по схеме, а не по предикату), и оно разнесёт и
  DSL, и IR, и адаптер. Тащить в заход с предикатами не стоит.

Попутно к починке: `generate-model.ts:85` жёстко пишет `field.ref ? 'number'`,
то есть ref на `bigint`-PK типизируется как `number`, хотя в базе `bigint`. Для
валидации это будет врать.

## Предлагаемая очередность

| # | Этап | Почему так |
|---|------|-----------|
| 1 | `f.text` / `f.uuid` / `f.bigint` + починка ref→`number` | снимает блокер «нечем объявить поле» |
| 2 | Правила на одном поле, двурежимный IR | декларативные правила двурежимные бесплатно |
| 3 | Кросс-полевые выражения | покажет реальную форму выражений |
| 4 | `injectWhere` как фильтр записи | отдельный тип правила, в аудите помечается как фильтр |
| 5 | `.validate()` терминалом + асимметрия типов | можно закрыть тестами без БД |
| 6 | Аудит: `app.validate.run()` + `kadmium validate` | первая видимая польза на живых данных |
| 7 | `CHECK`-констрейнты в `DbDdlAdapter` | единственное место, где инвариант настоящий |
